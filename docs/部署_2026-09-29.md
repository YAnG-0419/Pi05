| cam1：左腕 | 用户提供：**305**；IP、序列号待填 | ROS `/cam1/color/image_raw` → `observation/left_wrist_image`；RGB `480×640×3` |

当前代码不是通过相机 IP 选择设备，而是读取遥操仓库的 `data_collection/config/cameras.yaml`，要求 `cam0/1/2` 的语义依次为 `head/left_wrist/right_wrist`，且三个 `serial_number` 不同。头部 IP `192.168.35.35` 已由用户提供，但当前启动参数仍为空 IP、按序列号自动枚举；不能认为该 IP 已写入代码。当前可见的参考仓库只有 [`cameras.yaml.example`](/home/descfly/llx/gello_upper_body_teleop/data_collection/config/cameras.yaml.example)，其中序列号为 `REPLACE_*` 占位；没有可据此填写的真机序列号。正式接口清单应从现场实际 `cameras.yaml` 或设备枚举补齐。`--start-cameras` 用于启动相机；相机已有发布进程时不应重复启动。

具体链路是：OpenPI 的 `observe.py` 在需要时启动参考仓库的 ROS `triple_camera.launch.py`；该文件按 `serial_number` 绑定 `cam0/1/2`，再发布 `/cam0/1/2/color/image_raw`。驱动默认 `enumerate_net_device=true`、`net_device_ip` 为空，即自动枚举网络相机；它也支持显式网络 IP 参数。OpenPI 为三路话题各启一个订阅进程，转成 `rgb8` 后通过本机 Unix socket 送入观测缓存。启动相机的容器使用 host 网络，并挂载 `/dev`。若已有相机 ROS 发布进程，OpenPI 仅订阅，不再启动驱动。参见 [`triple_camera.launch.py`](/home/descfly/llx/gello_upper_body_teleop/ros_ws/src/teleop_camera_bringup/launch/triple_camera.launch.py)、[`gemini435_le.launch.py`](/home/descfly/llx/gello_upper_body_teleop/ros_ws/src/orbbec_camera/launch/gemini435_le.launch.py)、[`observation_sources.py`](/home/descfly/lpy/openpi/deploy/fr3_wuji/observation_sources.py)。

**型号适配待改：**当前 `triple_camera.launch.py` 把三路相机都交给 `gemini435_le.launch.py`，其 README 也按“三台 435Le”描述。用户提供的实际组合是头部 435、两台腕部 305；因此现有启动文件不能被视为已适配两台 305。需要确认 435/305 的准确型号、对应 ROS 驱动与话题/图像规格，再按相机类型分配启动文件并做只读采图验证。

**模型输入输出契约：**输入 `observation/state` 是 54 维实测关节位置（float32、弧度），顺序为 `[左臂7, 左手20, 右臂7, 右手20]`；另有上述三路 `rgb8` 图像和英文任务 `prompt`。服务输出 `50×54` 的绝对关节目标，顺序相同，不能再次叠加当前状态。左、右臂反馈来自 `/left/franka/joint_states`、`/right/franka/joint_states`；手部来自 SDK 实测或 `/teleop/wuji/{left,right}/joint_states`。双臂命令走 ROS `/teleop/arm_commands` 与安全网关，双手由独占的 Wuji SDK 进程发送。图像与状态按时间戳对齐，观测代码默认样本最大年龄 `0.2 s`、组内最大时间差 `0.08 s`、最新状态年龄 `0.15 s`。

部署结构现在分成公共运行层、三种速度方案与模型适配层；参数总表见 [`FR3_WUJI_ARCHITECTURE.md`](/home/descfly/lpy/openpi/deploy/FR3_WUJI_ARCHITECTURE.md)。

| 路径（均相对 `/home/descfly/lpy/openpi`） | 主要内容 |

| `deploy/fr3_wuji_runtime/` | 三种速度共用的启动命令、控制器核验、设备占用检查、进程清理与有期限 IPC。 |
| `deploy/fr3_wuji_slow/` | 慢速入口、规划、播放器、连续调度和配置；新维护位置。 |

新慢速命令是 `bash deploy/fr3_wuji_slow/run.sh ...`，原 `experiments/weight_motion_eval/oneshot/run.sh` 与旧 Python 导入仍可用。`oneshot` 只作为兼容名称保留，新增慢速实现请放在 `fr3_wuji_slow`。

### 速度方案的当前默认值

| 方案 | 模型节点 / 下发 | 规划或播放特点 | 臂部播放目标速度 / 跟踪误差 |
| --- | --- | --- | --- |
| 慢速 | 通常 30 Hz / 100 Hz | 曲线规划，`minimum-time-scale=2.5`，连续段间停稳 | `0.42 rad/s` / `0.08 rad` |
| 中速 | 19999/30000/30000v2 按 30 Hz 节点、25000 系列按 15 Hz 节点；设备均按 100 Hz 下发 | `minimum-time-scale=0.625`；连续模式默认约 25 秒后在**下一段边界**改用慢速轨迹参数 | `1.68 rad/s` / `0.2 rad` |
| 快速 | 30 Hz / 100 Hz | 默认RTG半段预取和cubic衔接；19999可显式选RTC模型引导+实际延迟跳步；可选serial | 19999默认无臂部回放动态上限，legacy为1/3/30；跟踪 `0.2 rad` |

中速切换后仍由中速设备会话持有机器人，不代表所有网关/设备限值一起切回慢速。三种入口共用设备占用锁，不能同时驱动真机。

| --- | --- | --- | --- | --- |
| 19999 | `:8001` | `checkpoints/pi05_fr3_wuji_weighted/tomato_lora_0918_a70_b30/19999` 等多个 19999 目录 | 原生 54 维 LoRA；使用所选 checkpoint 自带统计 | 慢 / 中 / 快 |
| 30000 | `:8002` | `checkpoints/30000` | 64 维 LoRA，适配 revision 2；状态和动作在模型内部为左臂、右臂、左手、右手、占位10 | 慢 / 中 |
| 30000v2 | `:8003` | `checkpoints/30000v2` | 64 维全量微调，沿用 revision 2 的顺序映射 | 慢 / 中 / 快（30000 目录的专用包装） |
| 25000 | `:8004` | `checkpoints/25000` | 64 维全量微调，revision 3；输入按真机顺序补零，输出重排到 54 维；配置为 15 Hz | 中 |

### 当前动作输出维度与频率

| 模型 | 模型原始动作 | 服务发给执行端 | 模型动作节点时间轴 | 设备控制下发 |
| --- | --- | --- | --- | --- |
| 19999 | `50×54` | `50×54` | 30 Hz | 100 Hz |
| 30000 | `50×64` | 适配后 `50×54` | 30 Hz | 100 Hz |
| 30000v2 | `50×64` | 适配后 `50×54` | 30 Hz | 100 Hz |
| 25000 | `50×64` | 适配后 `50×54` | 15 Hz（当前代码假设） | 100 Hz |
| 25000-single | `50×64` | 适配后 `50×54` | 15 Hz（当前代码假设） | 100 Hz |

`50` 是一次预测的动作节点数；`54` 是真机双臂双手的总关节数：左臂 7 + 左手 20 + 右臂 7 + 右手 20。执行端使用的单帧顺序固定为 `[左臂 0:7，左手 7:27，右臂 27:34，右手 34:54]`，数值是**弧度制的绝对关节目标**，不是在当前姿态上累加的增量。

30000/30000v2 的模型内部 64 维动作顺序是 `[左臂7，右臂7，左手20，右手20，占位10]`；服务端重排并去掉占位维度后才发出 `50×54`。25000/25000-single 的**动作输出**也按该 64 维顺序重排；它们的**模型状态输入**则按真机 54 维顺序补零至 64 维。19999 原生使用 54 维，无 64→54 适配。执行端对外只接收统一的 `50×54`，并校验形状与权重契约。

**15 Hz 与 100 Hz 是两层频率：**25000 系列的 50 个模型动作点按 15 Hz 时间轴解释；中速规划器生成 100 Hz 轨迹，控制循环约每 `0.01 s` 向设备提交一帧。`minimum-time-scale=0.625` 及速度/加速度/jerk 边界会改变实际播放时长，所以 15 Hz 不表示设备只以 15 Hz 接收命令，也不表示墙钟时间必然等于 `50/15 s`。25000 的 15 Hz 目前依据归一化资产目录名和代码配置，checkpoint 未带可独立核验的完整训练采样率记录。

服务和执行端会核对 checkpoint、归一化哈希、维度、顺序、适配版本及预热状态。历史脚本 `deploy/fr3_wuji_30000/serve_v2.sh` 默认让 **30000v2** 占用 `8002`，与独立 30000v2 服务默认 `8003` 不同，因此端口不能代替契约核对。

**当前目录中的默认路径缺口：**慢速入口与 19999 模型服务默认使用 `checkpoints/19999`；快速入口默认指向 `checkpoints/19999_269/19999`。这两个路径在当前树中不存在；实际使用 19999 时，服务端和执行端需明确指定**同一个**已存在的 checkpoint。中速选 19999 也需显式传 `--checkpoint`。

## 5. 当前机器需要补齐的现场信息

1. **相机身份与型号：**补齐三台的实际序列号、两台腕部 IP、435/305 的准确子型号；把 cam0/1/2 的真值及物理位置写入现场 `data_collection/config/cameras.yaml`。当前只找到占位模板，且启动文件三路都使用 435Le 驱动，需核对两台 305 的驱动、ROS 话题与图像尺寸。
2. **参考仓库路径：**执行代码硬编码 `/home/user/lpy/gello-retarget`，本机可见的遥操仓库却在 `/home/descfly/llx/gello_upper_body_teleop`，且当前参考仓库没有正式 `cameras.yaml`。本机直接照 README 的 `/home/user/lpy/Pi05` 命令运行会遇到路径不匹配；需要先确定实际部署机器的仓库挂载/路径配置。
3. **现场地址与设备状态：**确认四个默认地址、左右手身份、20 关节在线状态、相机序列号及控制器产物；25000 文档记录过右手 NID=8 的 `4099` 温度故障，使用前应确认已恢复。
4. **模型匹配：**确认服务端与执行端引用同一 checkpoint，握手的统计/模型契约一致；25000 系列的 15 Hz 需用训练记录复核。代码入口存在不等于该组合完成真机验收。

**交给同事开发时：**OpenPI 代码可以直接作为修改基础；完整运行还依赖参考遥操仓库、真实 `cameras.yaml`、ROS/Orbbec 容器镜像、Wuji SDK 环境、控制器构建产物和相应 checkpoint。当前代码把参考仓库路径 `/home/user/lpy/gello-retarget`、Wuji Conda 路径 `/home/user/miniconda3/envs/gello-upper-body-teleop` 写死在多个入口；换机器时应先改成统一的可配置路径，核对 Docker 挂载、CPU 集与网络，再做只读观测和离线检查。仅复制 OpenPI 文件夹并不能直接在另一台机器上采图或运行真机。

## 6. 真机输入输出契约

### 6.1 观测

| 输入 | 来源与模型键 |
|---|---|
| 左右臂实测位置 | `/left/franka/joint_states`、`/right/franka/joint_states` |
| 左右手实测位置 | SDK `read_position()`；或独立 Hand 执行进程发布的新鲜反馈 |
| 三路 RGB | cam0 → `observation/image`；cam1 → `observation/left_wrist_image`；cam2 → `observation/right_wrist_image` |
| 状态 | `observation/state`：`[左臂7、左手20、右臂7、右手20]`，54 维 float32，弧度 |

双臂按关节名称重排，手部按采集契约的 20 关节固件顺序。不要用目标命令冒充实测状态。RGB 使用 HWC、uint8，核对颜色及采集时视角。预处理沿用 openpi 等比例补边逻辑，先验证与服务端输入一致。

### 6.2 输出

输出每步为绝对关节位置，弧度：左臂 `0:7`、左手 `7:27`、右臂 `27:34`、右手 `34:54`。服务端已反归一化并将臂部 delta 还原，不要再次累加当前关节状态。

FR3：发往 `/teleop/arm_commands`，类型 `teleop_interfaces/msg/ArmCommand`。填写 `source=openpi`、session、递增 sequence、active_sides、joint_names、positions。双臂命令应重新拼成左臂7 + 右臂7；命令名称是 `left_fr3v2_joint1..7`、`right_fr3v2_joint1..7`，不要用数据集的名称代替。先在网关配置中加入来源 `openpi`，保留既有接管、限位和超时检查。

Hand 2：复用 `adapters/wuji/backend.py` 的 `WujiHand2Backend.send()`。训练手部命令已是固件顺序，不再调用 MANUS 重定向或重复应用关节排列变换。

**`/teleop/wuji/{side}/command` 是采集遥测，不是执行入口。** `teleop_hand_telemetry/receiver.py` 只有发布器，向该话题发消息不会让这份代码驱动手。原 Operator 退出后，其手部状态遥测也会消失，部署执行进程必须负责持续读反馈。

## 7. 尚需开发的模块

建议模型相关代码留在 openpi，真机执行与安全接入放在采集控制仓库的独立部署入口。以下名称仅为建议：

| 模块 | 必须完成的行为 |
|---|---|
| `observation_adapter` | 收集三路 RGB、实测关节；按时间戳同步；拒绝缺失/过期数据 |
| `policy_client` | 远程推理、预热、超时、错误处理和推理耗时统计 |
| `action_executor` | 与推理解耦，30 Hz 消费动作；首步和 chunk 衔接检查；异常时协调双臂双手 |
| `fr3_policy_source` | ArmCommand 会话、序号、名称；接入安全网关；读取命令接受/拒绝状态 |
| `hand_executor` | 唯一 SDK 所有者；命令/反馈本地协议；位置/速度约束、诊断、启停和命令过期处理 |
| 部署配置及入口 | IP、相机、关节映射、限值、运行时长；默认不执行动作；开始/暂停/停止 |
| 运行记录 | 观测时间、推理动作、实际下发值、反馈、队列状态、网关拒绝原因 |

模型 horizon 保持 50；30 Hz 下覆盖约 1.67 秒。可配置每次实际执行多少步再重规划，但须依据测得延迟设计，不要随意改模型配置。网关的 0.25 秒命令超时要求控制循环独立于阻塞推理。队列耗尽必须进入明确的保持/停止状态，不能无限重放旧 chunk 或伪造新鲜观测。

Wuji 参考仓库有 RTG broker，而当前 openpi 客户端没有；首版可用异步队列，之后再评估是否移植 RTG。现有 WebSocket 客户端接收会阻塞，需补充执行端独立的超时监控。

## 8. 联调和正式启动顺序

1. 两端依赖导入通过，假观测远程推理通过。
2. 在工控机核对 FCI 网络、实时配置、左右设备身份和相机对应关系。
3. 启动 GPU 服务并预热。
4. 使用待新增的部署入口启动 FR3、安全网关、相机、Hand 执行进程；保持策略输出关闭。
5. 运行真机只读推理，检查数据新鲜度、输出范围、首步跳变与端到端耗时。
6. 分别验证少量臂/手动作和停止行为，再做有限步数的双臂双手闭环。
7. 场景与初始姿态接近采集条件后，测试完整任务，对比 10000 和 19999 权重。

不要把 `start_wuji_teleop.sh` 或不带服务名的 `docker compose up` 当成策略部署启动命令：它们会拉起遥操或其他硬件服务。当前还没有一条已经完成并验证的真机策略启动命令。

停止遥操来源后再让策略接管；同一只手只能由一个执行进程持有。默认禁用硬件输出属于采集仓库现有约定；Hand 后端的构造参数 `auto_enable=True` 则需由新入口明确覆盖。注意 `auto_enable=False` 仍会连接设备并调用 disable，不属于纯只读网络测试。
